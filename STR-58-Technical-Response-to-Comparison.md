# STR-58 Technical Response to Comparison and EIC Test Findings

## Purpose and scope

This response systematically contextualizes the issues raised in:

- `dev-iteration-1-vs-STR-58-caller-module.md`
- `dev-iteration-1-vs-STR-58-root-module.md`
- `MK[STR-58]vsPR[STR-91].md`
- `STR-58-TEST-RESULTS.md`

The intent is not to dispute valid findings or criticize the comparison author. It is to separate demonstrated defects from environment-specific constraints and architectural choices, preserve the stronger implementation characteristics identified in STR-58, and define a practical convergence path.

## Executive position

The evidence does **not** establish that STR-58's AKS specification is invalid. It establishes that:

1. `network_mode = "overlay"` is an incorrect mapping to a Windows-only provider field and should be removed.
2. The tested EIC service principal cannot create Azure role assignments, so the tested IAM path cannot run in EIC without externally prepared RBAC.
3. Both EIC apply attempts stopped at role assignments. `azurerm_kubernetes_cluster.this` was never reached, so no conclusion about successful or unsuccessful AKS creation can be drawn from those attempts.
4. The root comparison says STR-58's role assignments are gated by `manage_role_assignments`. That weakens the broader claim that `identities.tf` must be removed entirely: a configurable externally managed IAM mode can satisfy EIC while retaining a reusable self-managed mode for environments that permit it.

The recommended base therefore remains STR-58, with a corrected network interface and an EIC-compatible prerequisite/IAM mode.

## Interpretation of the EIC test

The precise test conclusion should be:

> STR-58, in the tested configuration, could not proceed to AKS creation because the EIC deployment service principal lacked permission to create two required role assignments. The first plan also exposed an invalid `network_mode` input mapping, which must be removed. After the networking correction and external preparation or disabling of Terraform-managed IAM, the AKS resource must be retested end to end.

This wording preserves every demonstrated result without extending the evidence beyond what was actually executed. The test report records successful creation of both managed identities, failure of the two role assignments, and “Not reached” for the AKS cluster. It also explicitly states that the failure is not a bug in the AKS configuration (`STR-58-TEST-RESULTS.md`, lines 64–73 and 105–114).

## Recommended path

1. **Retain STR-58 as the AKS implementation base**, including its PRD/security profiles, node-pool controls, observability, addons, diagnostics, maintenance governance, mandatory tags, and preconditions.
2. **Remove `network_mode`** from the module interface and resource mapping. Continue using `network_plugin_mode = "overlay"` for Azure CNI Overlay.
3. **Support EIC's external prerequisite model**: accept pre-created control-plane/kubelet identities and resource groups, disable module-managed role assignments in EIC, and document PlatformOps/NIS IAM prerequisites.
4. **Verify `manage_role_assignments` behavior end to end**, including removal of dependency edges when false. Do not require deletion of `identities.tf` unless the final architecture chooses exclusively external identity ownership.
5. **Preserve the Naveen-requested broad tag ignore while it remains the approved decision**, but document its drift-management trade-off. Move to surgical volatile-tag ignores if governance requirements change.
6. **Adopt focused interface improvements** where required: configurable naming, supported private-DNS/public-FQDN mode, autoscaling bounds, and any confirmed EIC node-pool constraints.
7. **Retest end to end in EIC Azure Gov** after prerequisites are in place. The success criterion is an actual attempt of `azurerm_kubernetes_cluster.this`, followed by diagnostics, node pools, addons, outputs, and a clean subsequent plan.

## Conclusion

The comparison identifies a real `network_mode` defect and a real mismatch between the tested IAM path and EIC's restricted permission model. It does not demonstrate a failed AKS specification, because AKS creation was never attempted. The balanced engineering response is to correct the genuine defect, adopt EIC-compatible external prerequisites, preserve STR-58's substantially stronger production/security implementation, and then complete the end-to-end test that the current evidence explicitly says remains outstanding.
